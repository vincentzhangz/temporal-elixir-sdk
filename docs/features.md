# Feature compatibility

The comparison baseline is the behavior exposed by the
[official Temporal Go SDK](https://github.com/temporalio/sdk-go) and the
[official Temporal Rust SDK](https://github.com/temporalio/sdk-rust), not the
presence of generated protobuf modules. The Rust SDK is in Public Preview; its
documented gaps (side effects, memos, enhanced stack traces) are marked per row.

**Status definitions:** In the baseline columns, **Supported** means the
official SDK exposes the behavior, **Partial** means only a documented subset
is exposed, and **Unsupported** means the behavior is absent. In the Elixir
column, **Supported** means the stated narrow behavior has passing unit and
official-server integration evidence; **Partial** means only a documented
subset works; **In progress** means isolated implementation/tests exist but the
feature is not wired end to end; **Experimental** means evidence is narrow and
the API or behavior may change; **Unsupported** means no usable SDK behavior is
provided.

| Capability compared with the official Go and Rust SDKs | Go SDK | Rust SDK | Elixir status | Current evidence and limitations |
| --- | --- | --- | --- | --- |
| Transport, TLS, mTLS, metadata, and API-key auth | Supported | Supported | Supported | Pure-BEAM gRPC/Mint transport with verified TLS defaults, custom CA (`ca_cert`/`ca_certs`) and SNI (`server_name`) override, PEM-bytes mTLS, opt-in `verify: :verify_none`, HTTP/2 PING keepalive, connect timeout, 128 MiB message limit, per-call metadata/API-key providers, deadlines, status mapping, and opt-in idempotent retries. The transport is native (no vendored `grpc` dependency): framing, status/trailer mapping, keepalive, and message-size limits have unit coverage ([transport tests](../test/temporal/mint_transport_test.exs), [option tests](../test/temporal/connection_options_test.exs)). HTTP CONNECT proxies and DNS load balancing are not supported by the Mint stack. |
| Client start, result, and Continue-As-New | Supported | Supported | Supported | `Temporal.Client.start_workflow/4`, `execute_workflow/4`, `result/2`, and `result_with_run_chain/2` cover start/result and Continue-As-New run-chain following with run-cycle detection. Live-verified against an official server ([live tests](../test/integration/live_workflow_test.exs), [Continue-As-New tests](../test/temporal/continue_as_new_test.exs)). |
| Workflow execution and history replay | Supported | Supported | Supported | Named synchronous zero- or one-argument workflows, paginated Workflow Task history retrieval, serial history validation, task-token fencing, immediate completion, and offline replay share one typed event reducer and machine registry. Differential, page-boundary, and live nondeterminism-regression tests cover the shared path ([kernel tests](../test/temporal/workflow_kernel_v2_test.exs), [runtime tests](../test/temporal/workflow_runtime_test.exs), [replay tests](../test/temporal/workflow_replay_test.exs), [live tests](../test/integration/live_workflow_test.exs)). |
| Activities, heartbeats, cancellation, retries, and failures | Supported | Supported | Supported | Sequential and concurrent Activity execution, heartbeats with `cancel_requested` detection, typed failures, retry policy, retry exhaustion, non-retryable failures, and heartbeat-checkpoint resume. Async completion is supported via `Temporal.Activity.Async` ([live tests](../test/integration/live_workflow_test.exs), [Activity tests](../test/temporal/activity_ga_test.exs), [async tests](../test/temporal/activity_async_test.exs)). |
| Durable Workflow timers | Supported | Supported | Supported | `Temporal.Workflow.sleep/1,2`, `new_timer/1,2`, `await/1`, `cancel_timer/1`, logical `now/0`, `TimerOptions`, and timer cancellation scopes use deterministic IDs and history-backed `StartTimer`/`CancelTimer` machines. Unit/replay/live evidence covers zero and invalid durations, sub-millisecond rounding, command batching, multiple wakeups, Activity interleaving, cancellation races, and Continue-As-New ([API tests](../test/temporal/workflow_timer_api_test.exs), [machine tests](../test/temporal/workflow_timer_machine_test.exs), [replay tests](../test/temporal/workflow_timer_replay_test.exs), [live tests](../test/integration/live_workflow_test.exs)). |
| Signals and Signal-With-Start | Supported | Supported | Supported | `Temporal.Client.signal_workflow/3-5` and `signal_with_start/6` support workflow/run targeting, stable request IDs, headers, identity, structured conversion/RPC errors, and the generated unary transports. Workflow code can install/replace/remove named and dynamic handlers, access signal headers, mutate deterministic handler state, wait on that state, and wait for all handlers. History reduction buffers before registration, preserves FIFO event order, deduplicates request/event IDs, and keeps blocking handlers replay-safe across Workflow Tasks. Unit/property/replay/live coverage includes unknown signals, Signal-With-Start, timers, Activities, and Continue-As-New routing ([client tests](../test/temporal/client_signal_test.exs), [dispatcher tests](../test/temporal/workflow_signal_dispatcher_test.exs), [replay tests](../test/temporal/workflow_signal_replay_test.exs), [live tests](../test/integration/live_signal_test.exs)). |
| Queries | Supported | Supported | Supported | `Temporal.Client.query_workflow/3-5` supports workflow/run targeting with `:query_reject_condition`. Workflow code installs named handlers with `Temporal.Workflow.set_query_handler/2`; the worker answers queries attached to Workflow Tasks (via `query_results`) and legacy query-only tasks (via `RespondQueryTaskCompleted`), replaying the full history to reach the latest deterministic state. Unit and live coverage includes answered results, handler failures, unregistered types, and running-workflow queries ([query tests](../test/temporal/query_test.exs), [live tests](../test/integration/live_workflow_test.exs)). |
| Updates and Update-With-Start | Supported | Supported | Supported | `Temporal.Client.update_workflow/3-5` calls `UpdateWorkflowExecution` and `update_with_start/6,7` delivers the Update-With-Start semantic as an atomic `ExecuteMultiOperation` (start + update); `Temporal.Workflow.set_update_handler/2` registers deterministic handlers and update request messages on Workflow Tasks are dispatched and answered with `Acceptance`/`Response` protocol messages. Replay handles `WorkflowExecutionUpdateAccepted` / `...UpdateCompleted` / `...UpdateRejected` ([update tests](../test/temporal/update_test.exs), [client tests](../test/temporal/schedule_client_test.exs)). |
| Child workflows | Supported | Supported | Supported | `Temporal.Workflow.execute_child_workflow/3,4` and `await_child_workflow/1` emit `COMMAND_TYPE_START_CHILD_WORKFLOW_EXECUTION`; the `ChildWorkflow` machine resolves `StartChildWorkflowExecutionInitiated`, `ChildWorkflowExecutionStarted`, and the completed/failed/canceled/timed-out terminal events with unit + replay coverage ([child tests](../test/temporal/workflow_child_and_external_test.exs)). |
| External-workflow signals from Workflow code | Supported | Supported | Supported | `Temporal.Workflow.signal_external_workflow/4,5` emits `COMMAND_TYPE_SIGNAL_EXTERNAL_WORKFLOW_EXECUTION`; the `ExternalSignal` machine resolves `SignalExternalWorkflowExecutionInitiated`, `ExternalWorkflowExecutionSignaled`, and `SignalExternalWorkflowExecutionFailed` with unit + replay coverage ([external tests](../test/temporal/workflow_child_and_external_test.exs)). |
| Workflow cancellation and workflow failure | Supported | Supported | Supported | `Temporal.Workflow.fail_workflow/1` (emits `FailWorkflowExecution`) and `cancel_workflow/0` (emits `CancelWorkflowExecution`), with replay support for `WorkflowExecutionFailed` / `WorkflowExecutionCanceled` / `WorkflowExecutionCancelRequested` close events so Workflow code can observe cancellation ([cancellation tests](../test/temporal/workflow_cancellation_test.exs)). |
| Local, eager, and asynchronously completed Activities | Supported | Supported | Supported | Asynchronously completed Activities via `Temporal.Activity.Async.complete_async/3` / `fail_async/3`; eager Activity tasks dispatched via `Temporal.Activity.Worker.submit_eager/2` (and forwarded from Workflow Task completion `activity_tasks` when an `:eager_activity_worker` is configured); local Activities via `Temporal.Workflow.execute_local_activity/3` recorded as `LocalActivity` markers ([async tests](../test/temporal/activity_async_test.exs), [polish tests](../test/temporal/workflow_polish_test.exs)). |
| Sticky cache | Supported | Supported | Supported | Opt-in sticky task queues (`Temporal.Worker` `:sticky` option): the worker generates a per-worker sticky queue, polls it before the normal queue, and attaches `sticky_attributes` to Workflow Task completions ([worker tests](../test/temporal/worker_test.exs)). |
| Worker concurrency, shutdown, and versioning | Supported | Supported | Supported | The Workflow worker processes tasks concurrently (independent runs in parallel, per-run serialized via the run cache and task-token fencing), with graceful stop (`Temporal.Worker.stop/2` with a drain timeout), sticky queues, opt-in build-ID versioning (`:build_id`/`:use_versioning` setting `worker_version_capabilities` on polls and `worker_version_stamp` on completions), and concurrent Activity execution ([worker tests](../test/temporal/worker_test.exs), [async tests](../test/temporal/activity_async_test.exs)). Deployment versioning (worker versioning rules) is not exposed. |
| Data converters, payload codecs, and encryption | Supported | Supported | Supported | `Temporal.Converter` provides a pluggable encode/decode behaviour with a JSON/plain default; `Temporal.Codec` provides a payload-codec chain (with `Temporal.Codec.Base64` example) applied at the client start and Activity boundaries via the `:payload_codecs` connection option. Round-trip and option-validation tests cover both ([converter tests](../test/temporal/search_attributes_test.exs), [codec tests](../test/temporal/connection_options_test.exs)). |
| Client terminate, list, and describe workflows | Supported | Supported | Supported | `Temporal.Client.terminate_workflow/2,3`, `list_workflows/3`, and `describe_workflow/2` cover handle-based and by-ID targeting, reasons/details, page tokens, and raw describe responses with fake-transport unit evidence ([client operations tests](../test/temporal/client_operations_test.exs)). |
| Side effects | Supported | Unsupported | Supported | `Temporal.Workflow.side_effect/1` and `mutable_side_effect/3` record non-deterministic results into history via `SideEffect`/`MutableSideEffect` markers and return the recorded values on replay; `get_version/3` + `get_version_default/0` provide deterministic code versioning ([polish tests](../test/temporal/workflow_polish_test.exs)). The Rust SDK does not expose side effects. |
| Search attributes and memos | Supported | Partial | Supported | `Temporal.Workflow.upsert_search_attributes/1` and `upsert_memo/1` emit the upsert commands with replay support; `Temporal.Client.start_workflow/4` accepts `:search_attributes`/`:memo` and related options ([search tests](../test/temporal/search_attributes_test.exs)). |
| Schedules | Supported | Supported | Supported | `Temporal.ScheduleClient.create_schedule/5`, `describe_schedule/3`, `delete_schedule/3`, and `list_schedules/2` cover cron and interval schedules via the generated schedule RPCs ([schedule tests](../test/temporal/schedule_client_test.exs)). |
| Nexus | Supported | Supported | Partial | Workflow-side Nexus operations: `Temporal.Workflow.new_nexus_client/2` + `execute_nexus_operation/3,4` emit `COMMAND_TYPE_SCHEDULE_NEXUS_OPERATION` with replay support for the Nexus operation scheduled/started/completed/failed/canceled/timed-out events ([Nexus tests](../test/temporal/workflow_child_and_external_test.exs)). The Nexus worker is not implemented because the pinned `temporalio/api` v1.63.3 vendors `nexusservices/workerservice` as message-only (no service proto) — worker parity requires a newer API pin. |
| Interceptors and telemetry | Supported | Supported | Supported | `Temporal.Interceptor` provides `on_call`/`on_response` hooks and `Temporal.Telemetry` emits `[:temporal, :client, :call]` and `[:temporal, :worker, :poll]` events ([hooks tests](../test/temporal/test_environment_test.exs)). |
| Enhanced stack traces | Supported | Unsupported | Unsupported | Go exposes the enhanced stack trace workflow API; the Rust SDK does not. Elixir only carries the generated wire type, with no stack-trace RPC registered. |
| Testing, time skipping, and features harness | Supported | Supported | Supported | Unit tests, replay fixtures, opt-in official-server integration tests, `Temporal.TestEnvironment.run_workflow/3` (offline Workflow harness), and `Temporal.TestEnvironment.advance_time/3` (time-skipping that synthesizes timer history and re-reduces) exist ([harness tests](../test/temporal/test_environment_test.exs)). There is no cross-SDK features harness. |
| Temporal Cloud compatibility | Supported | Supported | Experimental | TLS, mTLS (PEM or file), API-key configuration, and custom CA/SNI primitives exist and are live-tested only against a plaintext local server; there is no verified Cloud conformance or compatibility claim. |

Last verified inputs: Temporal API **v1.63.3** and Temporal Server **1.31.2**.
See [the compatibility policy](compatibility.md) for the deliberately
limited claim. Unsupported history is rejected explicitly.

Every RPC carries Temporal's standard `client-name` and `client-version`
headers. The truthful community identifier is `temporal-elixir-community`; its
version is derived from the application version. These SDK headers are separate
from configurable client/worker `identity`.
